# 「不要用 flash」換一種語言還成不成立（2026-09-21）

[← 實測紀錄](README.md)

## 問題

kit 預設用 `deepseek-v4-pro`，不用比較便宜的 `deepseek-flash`。這個決定來自兩個真實 PR 上的單次對照（[README §4.2](../README.md#42-為什麼預設用-deepseek-v4-pro)），最關鍵的證據在 Shell：flash 的 4 個技術斷言錯了 3 個。

同一天的[三方對照](2026-09-21-three-way-review.md)在 Python 標的上得到相反的結果：7 個該報的點，flash 抓到 6 個，兩個誤報探針都沒中。但兩次之間，語言不同，有沒有專屬規則檔也不同（Python 有 `python.md`，Shell 沒有），推翻不了原本的決定。這次把兩種標的、兩個模型配齊，每組各跑 3 次。

## 跑前定好的事

兩份預期表都在跑之前定稿；跑完原文沒動，Shell 那份只在文末追加過一段更正（見下面的誤報探針）。

- **每個標的埋 10 個點**：7 個該報；2 個誤報探針——一個是前面已經擋掉的寫法，一個跟某個該報的點同形狀、只差一個條件；1 個預期不會報（缺測試）
- **判讀**：位置對、機制講錯的，不算命中
- **Shell 的重點格**：`if [ "$ahead" -gt 0 ]` 遇到空字串，bash 會印錯誤、條件當成假、那個分支不執行，腳本繼續往下跑（bash 5.3 實測）。預期表跑前寫的理由是「腳本沒有 `set -e`」；2026-10-03 實測才發現跟 `set -e` 無關（這個 `[` 寫在 `if` 的條件裡），判準不變。說「會中止」或「會當成 0」都算錯。原本的證據，就是 flash 把這類條件式的後果講錯

## 方法

- **標的**：Python、Shell 各一份合成 diff（104 行、101 行），都是整檔新增。Python 那份就是三方對照用的同一份
- **模型**：`deepseek-v4-pro`、`deepseek-flash`，關閉 thinking，`max_tokens` 16384；Python 標的套用 `python.md`
- **正式跑**：2 個標的 × 2 個模型 × 3 次，共 12 次。flash 在 Shell 標的上另外有 1 次試跑、3 次追加（為了查失敗原因），還有 1 次把 `max_tokens` 壓到 500 的截斷對照（沒有留下輸出）
- **評分**：09-21 用行號比對：finding 的行號落在哪個埋點附近，就算命中哪一個。之後按內容重看過：v4-pro 的全部 finding（09-24，看不到信心值與嚴重度）；2026-10-03 寫這頁時，又重看了 flash 在探針位置的 finding、flash 在 Python 的召回（2 次）、Shell 那次講到重點格的兩筆，以及 3 次失敗的原始輸出
- **花費**：17 次呼叫約 $0.11

## 結果

**「不要用 flash」維持，但證據比當時記的薄：flash 10 次裡至少 2 次吐出不合法的 JSON，v4-pro 6 次都合法；規則檔寫明不要報的，flash 兩次都報了。**

### 輸出解析得了嗎

| 模型 | 跑了幾次 | 當時解析得了 |
|---|---|---|
| `deepseek-v4-pro` | 6 | 6 |
| `deepseek-flash` | 10 | 7 |

flash 失敗的 3 次都在正式那 6 次裡（Python 1 次、Shell 2 次）。當時記成「API 回了沒收完的內容」；2026-10-03 用當時版本的解析程式，重跑 log 留下的原始輸出（每次前 2,000 個字元），三則錯誤訊息都一字不差重現，原因是：

- **Shell 那 2 次，flash 的 JSON 本身不合法**：summary 裡 `cd "$dir"` 的雙引號沒有跳脫，在第 178、185 個字元就斷了
- **其中 2 次還撞上我們自己解析程式的 bug**（Python 那次、Shell 其中 1 次）：它把 finding 內文裡的 code fence 當成整份回應的外包裝剝掉，切出錯的片段。Python 那次的 JSON 本身合不合法，log 只留了前 2,000 個字元，看不出來
- log 裡找不到「內容沒收完」的證據：當時記的「停在半個中文字」，原始輸出裡那幾個字後面是完整的

解析得了的 13 份輸出，內文都沒有 code fence。

### 召回

| 組別 | 解析得了的次數 | 平均抓到幾個（共 7 個，行號比對） |
|---|---|---|
| Python／v4-pro | 3/3 | 4.7 |
| Python／flash | 2/3 | 4.0 |
| Shell／v4-pro | 3/3 | 4.7 |
| Shell／flash | 1/3 | 6.0 |

行號比對會少算，也會多算：一筆 finding 同時講到兩個點只算一個、模型報錯行號又沒能重新定位的會漏算，位置對但講的是別件事的會多算。當時的比對腳本沒留下來，這些是推算的。按內容逐點重看，Python 上兩個模型每次抓到的都是同一組 6 個，都漏了迴圈裡的 HTTP 呼叫；v4-pro 3 次合計 18 個，行號比對算的是 14。Shell 的 v4-pro 按內容合計 14 個，跟行號比對一樣；flash 的 Shell 那一次，行號比對算 6 個，其中一個講的是 `cd` 成功之後沒切回原目錄，不是預期表的「`cd` 失敗沒檢查」，按內容是 4 或 5 個（看重點格那兩筆怎麼算），落在 v4-pro 3 次的 4～5 個之間。召回分不出高下。

### 誤報探針（按內容，只算正式那幾次）

| 探針 | v4-pro | flash |
|---|---|---|
| Python：上面兩行已經擋掉空清單，再取 `events[0]` | 1/3 | 0/2 |
| Python：可變預設值，但函式沒改過它（`python.md` 寫明不要報） | 0/3 | **2/2** |
| Shell：變數沒加引號，但前面已經用 regex 驗過格式 | 0/3 | 0/1 |
| Shell：跟重點格同形狀的算術比較，但有 `\|\| echo 0` 保底 | 1/3（機制講錯） | 1/1（講對了，見下） |

- **09-21 原本記的是「Python 標的上 flash 每次都同時中兩個探針」。** 那是行號比對的結果：flash 在第一個探針那一行，兩次報的都是事件沒排序，沒說空清單會出錯，其中一次明確引用了守衛。反倒是 v4-pro 有一次引用了守衛，又說空清單仍會出錯
- **可變預設值那格**：flash 兩次都報了，v4-pro 三次都沒報。flash 的說法不算錯——函式把預設的 dict 直接回傳出去，呼叫端改了就會污染下一次——但這支程式的呼叫端只讀不改，是潛在風險；規則檔寫明這種情況不要報，這格量的就是有沒有照例外條款走
- **Shell 最後一格的前提，事後發現有洞**：log 存在、但是空檔或只有空行時，`grep -c` 印出 `0` 又回傳失敗，`|| echo 0` 再補一個 `0`，變數變成兩行 `0`，比較就報錯（bash 5.3 實測）。flash 那一筆講的正是這個情況；v4-pro 那一筆說會得到空字串，機制錯
- **試跑與追加的 4 次不在表裡**（都是 flash、Shell 標的）：有 2 筆報了沒加引號，承認前面有 regex，卻還是說有風險，其中一筆舉的例子正是 regex 擋掉的字元；最後一格又講對 1 次

### 技術斷言：兩個模型都有講錯的時候

- **重點格**：flash 正式那次有兩筆講到它，一筆只說會報 integer expression expected、沒說會中斷；另一筆說「並使該次同步中斷」，後半錯。v4-pro 兩次都只說比較會出錯，而且都接著指出下游的 SQL 會拿到空值
- **標題寫錯**：兩個模型各有一筆，標題說 `local` 用在函式外，內文自己承認那行在函式裡
- v4-pro 另外有一筆把 SQL 的語法錯誤講成型別錯誤、一筆把迴圈的行為講錯

### 兩個模型都沒報的

正式那幾次：Shell 的固定 `/tmp` 路徑（symlink 攻擊、多個實例互相覆寫）、`cd` 失敗沒檢查（shellcheck 抓得到的那一個；flash 的試跑與追加各有一次報對），以及 Shell 的缺測試；後者再次印證 rubric「新增分支沒有對應測試」那條幾乎不觸發（[README §4.9](../README.md#49-rubric-的兩個實測限制)）。Python 的缺測試不算：`python.md` 寫明不要報。

## 限制

- Python 有專屬規則檔、Shell 沒有，所以 Shell 上的差別分不出是模型讀不懂 Shell，還是少了規則檔
- 每組只跑 3 次；Shell／flash 只有 1 次解析得了
- 合成標的、整檔新增，缺陷密度遠高於真實 code；題目是我們自己出、自己改
- 召回那張表是行號比對算的；按內容重看的是 v4-pro 的全部 finding、flash 在 Python 的召回與探針位置的 finding、Shell 那次講到重點格的兩筆，以及 3 次失敗的原始輸出；flash 在 Shell 的其他 finding 沒有逐筆重看。重看的是語言模型（Claude），被評的也是語言模型
- 失敗那 3 次，log 只存了原始輸出的前 2,000 個字元；截斷對照沒有留下輸出

## 因此改了什麼

- kit 的預設維持 `deepseek-v4-pro`
- 這次撞到的解析 bug（把 finding 內文裡的 code fence 當成整份回應的外包裝），`v1.3.0` 修掉了；當時是隔天另一次真實事故才找到它，那時沒發現這裡也有 2 次撞上它（Shell 那次 JSON 本身就不合法，修了照樣失敗；Python 那次看不出來）（[CHANGELOG 1.3.0](../CHANGELOG.md#130---2026-09-22)）。同一版也把解析失敗時的 log 改成頭尾都印、標明總長度
