# 把改動所在的整個函式一起送，抓得比較多嗎（2026-09-30）

[← 實測紀錄](README.md)

## 問題

kit 送給模型的 diff，每個改動上下各帶 3 行（`git diff --unified=3`）。修改型 PR 上，有些缺陷要看到函式的其他部分才判斷得出來。把改動所在的整個函式一起送，功能缺陷會不會抓得比較多？

這是「給模型更多 code」最簡單的做法：每個 PR 還是只呼叫一次，只是送出去的 diff 變長。

## 跑前定好的事

判準在呼叫 API 之前寫定，之後沒改。

- **分母**：Qodo 的功能性缺陷 309 則，全部算，包括不在 diff 裡的。finding 不分信心高低全部算（v1.6.0 起摘要列出全部 finding）
- **判「較好」，兩條都要成立**：
  1. 報到「同一個問題」的缺陷，函式上下文比基準多 10 則以上（約 3 個百分點）。兩臂各盲標一輪
  2. 位置命中：函式上下文兩輪裡低的那一輪，還是高於基準三輪裡高的那一輪。這條是為了擋掉單輪的運氣
- **判「較差」**：反過來，少 10 則以上，而且函式上下文兩輪裡高的那一輪，還是低於基準三輪裡低的那一輪
- 其他情況：分不出來。只有「較好」才另開計畫，把它做進 kit

## 方法

- **資料與兩層命中的定義**：同[修改型 PR 的基準線](2026-09-25-qodo-bench.md)（Qodo PR-Review-Bench，100 個修改型 PR）
- **兩個臂只差送出去的 diff**：
  - 基準：資料集附的 diff（上下各 3 行）
  - 函式上下文：在同樣兩個 commit 上用 `git diff -W` 重產。先驗過本機產的 3 行版本跟資料集附的 100/100 相同（hunk 標頭的函式名稱除外）
  - 函式邊界用 git 內建的語言規則。JS／TS／Swift 沒有內建規則，class 裡的方法會擴成整個 class；這次沒有另外寫規則
  - 只擴程式碼檔。JSON、YAML、lock、markdown 這類檔案沒有函式結構，`-W` 會把整個檔案塞進來，所以沿用原本的區塊
  - 擴完超過 kit 截斷門檻（40 萬字元）的 5 個 PR 整份退回原本的 diff，另有 3 個沒有東西可擴，實際不同的是 92 個 PR。送出的字元數合計 ×2.35，每個 PR 的中位數 ×1.79
- **其他全部相同**：rubric v1.4.0（現行版本）、`deepseek-v4-pro`、參數照 CI。函式上下文那一臂的 finding，用它自己送出去的 diff 定位
- **基準三輪**：基準線那兩輪，加上同一天新跑一輪，用來分開「上下文的效果」跟「API 那端的模型有沒有變」。基準線之後 kit 的程式改過，先比對過送出的內容，100 個 PR 逐字相同
- **盲標**：函式上下文第一輪跟基準新跑那輪的全部候選配對，共 897 組，混在一起打亂後分給 9 個標記員（語言模型）。配對編號看不出來自哪一臂，標記單不含信心值、嚴重度、輪次。看到標記結果之前，另一個獨立的標記者（同樣是語言模型）先抽 30 組標：「是不是同一個問題」30/30 一致，細分類 29/30
- **花費**：新跑的三輪約 $1.71（DeepSeek 離峰價）

## 結果

**判決：分不出來。** 「較好」不成立：同一個問題只多 4 則。「較差」也不成立：位置命中那條成立（函式上下文兩輪都低於基準三輪），但同一個問題沒有少 10 則。

| 功能性缺陷 309 則 | 函式上下文 | 基準 |
|---|---|---|
| 報到同一個問題（盲標的那一輪） | 134 | 130 |
| 位置命中（每一輪） | 163／154 | 177／178／175 |

「分不出來」只回答了判準那兩條，而這兩條的方向其實不一樣：同一個問題沒差，位置命中偏低。看到結果之後，我們把它們拆開來看（2026-10-01，不在跑前的判準裡）。

### 功能缺陷：抓到的一樣多

- **134 則落在基準兩輪之間**：新跑那輪 130，基準線第一輪 137（[基準線頁](2026-09-25-qodo-bench.md)的 44.3%，5 天前另一批標記）。逐則對照，函式上下文有 34 則是基準沒抓到的，基準有 30 則是函式上下文沒抓到的
- **位置命中兩輪都偏低**：平均每輪少約 18 則，基準三輪之間最多只差 3 則。位置命中本來就是上限：位置對、講的卻是別的問題，也算在裡面
- **有盲標的那一輪，少掉的多半不是漏報**：

  | 有盲標的那一輪（功能性） | 函式上下文 | 基準 | 差 |
  |---|---|---|---|
  | 位置對，也是同一個問題 | 121 | 124 | −3 |
  | 位置對，講的是別的問題 | 42 | 51 | **−9** |
  | 同一個問題，沒算到位置命中 | 13 | 6 | +7 |

- **另一輪少得更多**：比基準新跑那輪少 21 則。這一輪沒有盲標，拆不開
- **定位只解釋得了一小部分**：程式定位時，片段在 diff 裡出現不只一次就不猜，上下文變長之後這種情況多了一些。函式上下文的 finding 改用原本的 diff 定位，兩輪各多 6 則和 3 則；或把「片段出現不只一次，但模型給的行號就在標準答案旁邊」也算成命中，兩臂各多 5～9 則。兩種算法下，平均每輪的差距還有 13.7 和 18.5 則（原本 18.2）。「位置對、講的是別的問題」為什麼變少，原因沒查

### 違反 repo 規則：偏低，證據不夠

| 違反 repo 規則 271 則 | 函式上下文 | 基準 |
|---|---|---|
| 報到同一個問題 | 23 | 37（基準線第一輪 29） |
| 位置命中（每一輪） | 68／71 | 74／76／81 |

兩項都比基準的每一輪低，但基準兩輪的「同一個問題」自己就差 8 則。算是方向一致的跡象，還不到確定。

### 代價

送出的 token 多 89%。另外有 1 個 PR 第一次跑時，輸出被長度上限截斷（照續跑的設計重跑一次就成功）。

**一句話：把整個函式一起送，沒有量得到的收益，只有確定的代價。**

## 限制

- 只量了一種補上下文的方式：預先把所在函式（JS／TS／Swift 是整個 class）一起送、單次呼叫。讓模型自己決定要去看哪些 code 的做法，沒有量
- 資料集的缺陷大多注入在改動的那幾行；需要看函式其他部分才判斷得出來的有多少，不知道。上下文的好處可能被低估，也可能被高估
- 每臂只盲標一輪，分不出小於約 10 則（3 個百分點）的差別
- 拆開來看的那部分是看到結果之後才做的，前後比了約 36 組，沒有做多重比較校正
- 基準線第一輪的標籤是另一批標的。同一批配對重標過一次，「是不是同一個問題」413 組有 407 組一致（[v1.4.0 那頁](2026-09-28-v140-exit.md)）
- 只量了 recall，理由同[基準線頁](2026-09-25-qodo-bench.md)
- 資料集 2026-02 公開，可能被模型看過；標記員與被評的都是語言模型

## 因此改了什麼

kit 沒改，也不加「函式上下文」這個選項。

## 沒公開的部分

模型輸出、標記單與腳本放在不進 repo 的私有目錄。
