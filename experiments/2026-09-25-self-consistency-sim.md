# 同一份 diff 跑幾次再投票，划不划算（2026-09-25）

[← 實測紀錄](README.md)

## 問題

有些 AI review 的做法會把同一份 diff 跑好幾次，再投票或取聯集：多數次都報的才貼，或任何一次報過的都列出來。kit 對同一份 prompt 只呼叫一次。改成跑 3 次，能改善什麼、改善不了什麼？

這組沒有呼叫 API：用已經標好對錯的既有輸出重算，花費 $0。

## 方法

- **資料**：三個合成標的（Python 兩份、Shell 一份，都是整檔新增）。v1.4.0 的 rubric 每個標的跑了 10 次；前一版 rubric 跑了 9～10 次，當第二組資料，看換一版 rubric 結論還在不在。每筆 finding 在 09-24 那組實驗裡已經標過成立或不成立（規則判得了的自動標，其餘盲標）
- **「同一個 finding」怎麼認**：
  - 行號分群（程式做得到）：同一個檔、行號差 2 行以內，跨次串起來
  - 依內容分群：標記時依內容分的群，當參照
  - 片段分群（另一種程式做法）：引用的程式碼有一行相同
- **投票模擬**：從 10 次裡抽 3 次，同一群至少 2 票、而且群裡最高的信心 ≥ 0.7，才貼成行內留言；跟當時的預設「單次、信心 ≥ 0.7 貼成行內留言」比（`v1.6.0` 起預設只貼摘要）
- **嚴格口徑**：有爭議的算不成立

## 結果

### 兩次跑報的東西重疊多少

任兩次跑報出的問題（依內容分群），重疊程度（Jaccard）的平均，v1.4.0 是：Python 0.76、Shell 0.65、陷阱最多的那份 Python 0.63。也就是任兩次的聯集裡，有 24～37% 只出現在其中一次。前一版 rubric 在陷阱最多的那份只有 0.45。

### 投票：行內留言沒有穩定變準

| 標的 | 當時的預設：單次、信心 ≥ 0.7 | 3 次、≥ 2 票且信心 ≥ 0.7 | 3 次取聯集的 recall |
|---|---|---|---|
| Python | P 0.762／R 0.588 | P 0.803／R 0.617 | 0.625（單次、含摘要表 0.600） |
| Shell | P 0.932／R 0.629 | P 0.928／R 0.743 | 0.857（單次、含摘要表 0.700） |
| 陷阱最多的 Python | P 0.833／R 0.267 | P 0.818／R 0.294 | 0.431（單次、含摘要表 0.267） |

（P 是 precision；R 是 recall，只算埋好的缺陷。v1.4.0 的 rubric，行號分群）

- **行內留言那層的 precision 沒有穩定改善**：3 個標的 × 2 版 rubric 共 6 格，跟單次的信心門檻比，差 −0.015 到 +0.05
- 行內那層的 recall，v1.4.0 三份都升了一點（+0.03～+0.11）
- **聯集拉得動 recall**（Shell、陷阱最多的那份各 +0.16），代價是摘要表變長、變雜（行號分群）：每次的筆數 Python 6.4 → 8.0、Shell 6.9 → 8.4、陷阱最多的那份 4.2 → 7.6；precision 分別 0.766 → 0.667、0.884 → 0.828、0.714 → 0.667
- **成本 ×3**
- 行內那層，行號分群跟依內容分群差不多：差距都在 0.06 以內，有好幾格行號分群反而比較高。聯集那層差得比較多，例如 Shell 的 precision，行號分群 0.828、依內容分群 0.766。行號分群混到不同問題的群佔 6.6～8.1%
- 片段分群在 Python 的 recall 從 0.62 掉到 0.49。掉的剛好是一個埋點（裸 `except`）：那兩行太短，被比對規則排除，一次也串不起來

### 一致性當排序訊號

拿「3 次裡有幾次報」排序、同票數再看信心值，分對錯的能力（AUC）：

| rubric | 只看信心值 | 3 次的一致性優先、同票數再看信心值 |
|---|---|---|
| v1.4.0 | 0.876 | 0.904 |
| 前一版 | 0.829 | 0.910 |

（同一批抽樣；這張表用依內容分群，行號分群的版本沒有算）

前一版多 +0.081，v1.4.0 只多 +0.028，沒過我們改 rubric 時用的 +0.05 門檻。

### 投票消不掉的誤報

v1.4.0 的 rubric 下，明確不成立的 19 筆裡，有 8 筆是「一半以上的跑都會報」的同一個問題：把操作者自己設定的 webhook 環境變數當成外部輸入。前一版 rubric 明確不成立的 7 筆裡，沒有一筆是「一半以上的跑都會報」的。

這是信任邊界誤判。本 repo 的真實 PR 上也出現過同一型：把 repo 擁有者自己填的 lint 指令當成外部輸入。這個 webhook 的問題在 v1.4.0 下 10 次報 8 次，投票消不掉。要讓模型知道這類值是誰控制的，得在給它的資訊裡寫明；這組沒有測這條路。

另外，同一個問題在前一版 rubric 9 次跑只出現 1 次；在 v1.4.0 的 10 次跑出現 8 次，其中 5 筆信心 ≥ 0.7、會貼成行內留言。但這是在約 50 個問題裡事後挑出來的，只能當假說；[v1.4.0 那頁](2026-09-28-v140-exit.md)的限制也記了這一點。

## 限制

- 標的全是合成的，而且都是整檔新增：模型本來就看得到整個檔案，量不到「補上下文」這類做法
- 「3 次」是從 10 次跑裡抽的，不是真的各自獨立跑 3 次
- 依內容分群本身也用了「行號差 2 行以內＋內容比對」，不是完全獨立的參照
- 自動標記在幾個項目上會套錯（多在陷阱最多那份，Shell 也有一項）：只看位置與關鍵字、不看 finding 講的後果（10-01 在[另一組實驗](2026-10-01-prompt-hygiene.md)發現）。這組用的是 09-24 的標記，沒有重看，precision 與 AUC 可能偏高，陷阱最多那份最明顯
- 修改型 PR 上，同一個 PR 兩輪的重疊程度中位數是 0.40（[基準線頁](2026-09-25-qodo-bench.md)），但那是位置配對、每個 PR 算一次，跟這裡依內容分群的平均量法不同，不能直接比。投票在修改型 PR 上的效果，這組沒有量

## 因此改了什麼

kit 沒改成多次取樣，同一份 prompt 還是只呼叫一次。
